# 권한과 변경 경계

## 보존할 원칙

- 사용자 식별은 유효한 서버 세션과 현재 명단 기준이다. 브라우저의 이름·직책·부서 값은 권한 근거가 아니다.
- 담당 관계는 부서 → 지역 → 직책 순으로 해석하고 겸직 범위를 합친다. 지역 현황은 다른 부서와 섞지 않는다. 빈 지역을 무제한 권한으로 해석하지 않는다.
- 명단·통계의 전체 조회와 상담 원문·센터 서류의 담당 범위 접근을 분리한다.
- 센터 승인/전달은 기존 전체 담당 방식과 직책별 부서·지역 방식 두 정책을 준비했다. 확정 전 임의로 한쪽을 운영에 적용하지 않는다.
- 교육은 과정/정기교육/모임별 `settings`, `members`, `schedule`, `attendance`, `assignments`, `exams`, `reports` 위임을 구분한다. Telegram 방 관리자 여부와 앱 업무 권한은 별개다.
- 교육·전도 담당의 내보내기와 전도 담당의 등급 변경은 기존 서버 검사·확인·감사를 유지한다. 다운로드 권한을 단순 일반 관리자 판정으로 대체하지 않는다.
- 최종 책임자만 A/B 배정을 관리하고 자신의 A/B 화면을 선택한다. 다른 관리자도 배정 대상이지만 관리자는 아니다.
- 최초 PIN 등록은 명단 대조와 기존 전화번호 추가 대조, 번호 없는 계정의 새 번호/PIN 등록을 구분한다. 입력 번호는 문자 소유 인증 완료가 아니다. 분실·선등록 신고는 담당자 확인 후 복구하며 번호 일치만으로 자동 복구하지 않는다.

## 공동 개발 범위

교육 기능의 HTML/React 화면, 공통 서버의 해당 기능 처리, 테스트, 추가 SQL 제안은 원 개발 측이 개발할 수 있다. 아래 기반 자체의 변경은 전환 담당과 조율한다.

- 공통 인증·PIN·세션·책임자 판정과 권한 위임 기반
- A/B 경로·배정·전체 A 복귀·서비스 워커·PWA 진입
- Telegram 자동 예약·봇·웹훅·발송 책임
- 백업·복원·감시 인증·실패 알림
- 비공개 R2·기존 공개 파일 URL·다운로드 접근

운영 적용 전에는 실제 책임자 ID를 서버 설정으로 연결해야 한다. 공유 코드의 미설정 상태를 이름·가짜 번호·임의 관리자 허용으로 우회하지 않는다. 계정 식별값 자체가 인증 수단이 되는 것도 아니다.

이번 저장소 공유는 배포·운영 DB·실제 배정·외부 발송 승인과 별개다. 인증/권한 수정이 필요하면 구체적인 변경안과 정상/거절 검증을 PR에 담는다.
